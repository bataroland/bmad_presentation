📅 Hétfő reggel · Becslés: "2 nap, max 3"

📅 Hétfő délután · pom.xml átírva, 200 compile error

📅 Kedd · "findOne() nem létezik?! De a Spring docs szerint..."

📅 Szerda · sed-del cseréltük a javax-ot, az SSL eltört 💀

📅 Csütörtök · Tesztek zöldek, de a JSON formátum más lett

📅 Péntek · "Holnap újra próbáljuk" → következő szprint

Szétszórt jegyzetek · Nem dokumentált döntések · Production-ben felfedezett bugok

"Ismerős? A legtöbb csapat így migrál: 'majd kitaláljuk menet közben.' Egy egyszerű pom.xml csere → kaszkádos hibák. Szerdai SSL-eset: később megmutatom miért. NE menj bele részletesen — még csak a fájdalmat építjük."

Minden döntés indokolva és visszakövethető.

Lassan minden ADR. Magyarázd: "Az ADR-001 a fázisos megközelítést rögzíti — miért nem direkt ugrás. Az ADR-008 a Paketo döntést — miért nem Dockerfile. Minden ADR-ben benne van: kontextus, döntés, indoklás, következmény. Egy év múlva valaki megnyitja és érti."

Fázisos migráció — Phase Gate-ekkel

Phase 1 · Spring Boot 1.5 → 2.7

findOne() removal · context-path rename · JUnit 4→5 · Error handling centralizáció

🚪 Gate: green build + response spot-check

Phase 2 · Spring Boot 2.7 → 3.x

javax → jakarta · java.time migráció · SpringDoc · Lambdák, streams

🚪 Gate: green build + full response parity + namespace grep

Phase 3 · Containerization

WAR → JAR · Paketo buildpack · Devcontainer Java 25

🚪 Gate: container response parity = JAR response parity

Miért nem egyetlen ugrás?
Ha 5 breaking change egyszerre csap le → nem tudod, melyik tört el.
Izoláció · Validáció · Rollback

Minden fázis külön fragment. Magyarázd: "Phase 1: csak a framework API változások. Phase 2: csak a namespace és modernizáció. Phase 3: csak a packaging. Mindegyik végén GATE — nem mész tovább, amíg nem zöld. Rollback: branch revert, main érintetlen."

⚠️ A javax.crypto csapda

Emlékeztek a szerdai SSL eseményre az elején? Ez az.

❌ A naiv megközelítés

$ sed -i 's/javax/jakarta/g' \
       src/main/java/**/*.java

javax.persistence → jakarta.persistence ✓
javax.validation → jakarta.validation ✓
javax.crypto → jakarta.crypto ❌
javax.net.ssl → jakarta.net.ssl ❌

Kriptográfia eltört. TLS eltört.
Production deploy → security incident.

✅ A BMAD megközelítés

PRD FR6 explicit kimondja:

FR6: Migrate javax.* to jakarta.*
     EXCEPT JDK-owned packages
     (javax.crypto, javax.net.ssl,
      javax.security.*) — NEVER rename

A Pre-mortem Analysis derítette ki
a tervezési fázisban.

Felderítve a tervezésnél.
Nem production-ben.

FONTOS: Itt jön a "wow moment". Lassan vezesd be: "Emlékeztek? A szerdai napon a sed csere — itt van miért volt baj. A javax.crypto JDK-tulajdonú, nem kell migrálni. Egy egyszerű sed cseréli — és tönkremegy a kriptó. Ki csinált volna sed cserét? Legyetek őszinték. A BMAD-ban ez a Pre-mortem Analysis-ben derült ki, MIELŐTT egy sort módosítottunk volna."

A kód diff — tiszta, fázisonkénti

Before (Java 8)

import javax.persistence.*;
import java.util.Date;

@Entity
public class Book {
    @Temporal(TemporalType.DATE)
    private Date publishedDate;

    private Date createdAt;

    public List<Book> getBooksSortedByAuthor() {
        return books.stream()
            .sorted(new Comparator<Book>() {
                public int compare(Book a, Book b) {
                    return a.getAuthor()
                        .compareTo(b.getAuthor());
                }
            })
            .collect(toList());
    }
}

After (Java 25)

import jakarta.persistence.*;
import java.time.LocalDate;
import java.time.LocalDateTime;

@Entity
public class Book {
    private LocalDate publishedDate;

    @JsonFormat(pattern="yyyy-MM-dd'T'HH:mm:ss")
    private LocalDateTime createdAt;

    public List<Book> getBooksSortedByAuthor() {
        return books.stream()
            .sorted(comparing(Book::getAuthor))
            .toList();
    }
}

Nincs 500 soros "migration commit" — minden commit egy BMAD story végrehajtása.

"Ez egy konkrét fájl: Book.java. Ha a két oszlopot nézitek: javax→jakarta, Date→LocalDate, anonymous Comparator→method reference. Mindegyik VÁLTOZÁS külön commit, külön fázisban. A diff tiszta — egy code review-er pontosan tudja, mi miért történt."

/bmad-agent-builder — Saját agent
pl. "DevOps Engineer" agent a saját pipeline-odhoz

/bmad-workflow-builder — Saját workflow
pl. ".NET Migration" workflow .NET 6 → 8 átálláshoz

/bmad-module-builder — Komplett modul
pl. "FinOps" modul cég cost-management-hez

/bmad-customize — Built-in agent override
céges szabályok ráhúzása a meglévő agentekre

A BMAD nem zárt. Testreszabható. Bővíthető.

"A BMB a meta-szint. Nem csak HASZNÁLOD a beépítettet — építhetsz saját agentt, workflow-t, sőt modult. Egy 'DevOps Engineer' agent a CI/CD pipeline-odhoz. Egy '.NET Migration' workflow. A customize-zal pedig a céges szabályok ráhúzhatók a built-in agentekre."
